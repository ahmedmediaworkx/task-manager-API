# Task Manager API

Containerized REST API for managing private projects and tasks. The service is built with Express and TypeScript, uses PostgreSQL through Prisma, and provides JWT bearer authentication, Zod validation, Swagger UI, and Vitest integration tests.

Created by **Ahmed Wael (Abomorad)**.

## Features

- User registration, login, and current-user endpoints
- Private projects and tasks scoped to their owner
- Task filtering, searching, pagination, sorting, status, priority, and due dates
- PostgreSQL persistence with Prisma migrations
- OpenAPI documentation through Swagger UI
- Docker multi-stage production image
- Docker Compose environment with PostgreSQL, migrations, and API health checks
- GitHub Actions workflow for publishing images to GitHub Container Registry

## Technology

- Node.js 22
- TypeScript
- Express 5
- PostgreSQL 17
- Prisma 6
- Docker and Docker Compose
- GitHub Actions
- GitHub Container Registry (`ghcr.io`)

## Quick Start With Docker

### Requirements

- Docker Desktop with Docker Compose
- Git, if cloning the repository

Start the database, apply Prisma migrations, and start the API:

```bash
docker compose up --build -d
```

The services are available at:

| Service | URL |
| --- | --- |
| API | http://localhost:3000 |
| Swagger UI | http://localhost:3000/docs |
| Health check | http://localhost:3000/health |
| PostgreSQL | localhost:5432 |

Check service status:

```bash
docker compose ps
```

View API logs:

```bash
docker compose logs -f api
```

Stop the stack while retaining database data:

```bash
docker compose down
```

Stop the stack and delete the PostgreSQL volume:

```bash
docker compose down --volumes
```

The `migrate` service runs `prisma migrate deploy` once the database health check passes. It must exit with status `0` before the API starts.

## Configuration

Docker Compose reads variables from a local `.env` file. A typical development configuration is:

```env
POSTGRES_USER=task_manager
POSTGRES_PASSWORD=change-this-password
POSTGRES_DB=task_manager
POSTGRES_PORT=5432
JWT_SECRET=replace-with-at-least-32-random-characters
JWT_EXPIRES_IN=1h
PORT=3000
```

`DATABASE_URL` is assembled inside Compose using the `database` service hostname. Do not use `localhost` for the database host from the API container.

For production, set a strong `POSTGRES_PASSWORD` and a randomly generated `JWT_SECRET` of at least 32 characters. Do not commit `.env` files or production secrets.

## Build And Run The Image Manually

Build the API image:

```bash
docker build --tag task-manager-api:local --target runtime .
```

The image expects these runtime variables:

```bash
DATABASE_URL=postgresql://USER:PASSWORD@HOST:5432/DATABASE?schema=public
JWT_SECRET=replace-with-at-least-32-random-characters
JWT_EXPIRES_IN=1h
PORT=3000
NODE_ENV=production
```

Apply migrations before starting a manually run API container:

```bash
docker build --tag task-manager-api-migrate:local --target migrate .
docker run --rm \
  --network host \
  -e DATABASE_URL="postgresql://USER:PASSWORD@localhost:5432/DATABASE?schema=public" \
  task-manager-api-migrate:local
```

## GitHub Container Registry

The workflow at `.github/workflows/publish-image.yml` builds and publishes the Docker image to GitHub Container Registry.

### Automatic publishing

The workflow runs when:

- Code is pushed to the `main` branch
- A version tag matching `v*.*.*` is pushed, such as `v1.0.0`
- The workflow is started manually from the GitHub Actions tab

The published image name is:

```text
ghcr.io/ahmedmediaworkx/task-manager-api
```

Image tags include:

- `latest` for the default branch
- The Git commit SHA
- Semantic version tags for releases, such as `1.0.0`, `1.0`, and `1`
- A branch tag generated by Docker metadata

### Publish a release image

```bash
git tag v1.0.0
git push origin v1.0.0
```

Pull the published image:

```bash
docker pull ghcr.io/ahmedmediaworkx/task-manager-api:latest
```

For a private package, authenticate first:

```bash
echo "$GITHUB_TOKEN" | docker login ghcr.io -u YOUR_GITHUB_USERNAME --password-stdin
```

The workflow uses the built-in `GITHUB_TOKEN` with `contents: read` and `packages: write` permissions. No separate registry password is required for publishing from GitHub Actions.

## API Endpoints

Authentication:

- `POST /api/v1/auth/register`
- `POST /api/v1/auth/login`
- `GET /api/v1/auth/me`

Projects:

- `GET /api/v1/projects`
- `POST /api/v1/projects`
- `GET /api/v1/projects/:projectId`
- `PATCH /api/v1/projects/:projectId`
- `DELETE /api/v1/projects/:projectId`

Tasks:

- `GET /api/v1/projects/:projectId/tasks`
- `POST /api/v1/projects/:projectId/tasks`
- `GET /api/v1/tasks/:taskId`
- `PATCH /api/v1/tasks/:taskId`
- `DELETE /api/v1/tasks/:taskId`

Send the access token returned from login or registration as:

```http
Authorization: Bearer <token>
```

## Local Development Without Docker

Requirements:

- Node.js 20 or newer
- PostgreSQL 14 or newer

Install dependencies and configure the environment:

```bash
npm install
```

Create a local `.env`, set `DATABASE_URL` to a PostgreSQL database, and then run:

```bash
npx prisma migrate dev --name init
npm run db:seed
npm run dev
```

Available commands:

| Command | Purpose |
| --- | --- |
| `npm run dev` | Start the development server with reload |
| `npm run build` | Compile TypeScript into `dist` |
| `npm start` | Run the compiled server |
| `npm run typecheck` | Check TypeScript types |
| `npm run lint` | Run ESLint |
| `npm test` | Run integration tests |
| `npm run db:generate` | Generate the Prisma client |
| `npm run db:migrate` | Create or apply a development migration |
| `npm run db:seed` | Insert local sample data |

Integration tests clear application tables and require a separate test database. Never point them at a database containing valuable data.
